# 案例模板：事故报告（incident report）

**适用场景**：板子冻结 / oops / 设备故障锁存 / 构建事故。**用法**：复制本模板，每一节必填；“未覆盖项”不许空。
**已验证效果**：案例 05、09 用这个结构写成，读者无需追问就能知道原因、修法和还没验证的部分。**失效条件**：事故现场证据已丢失（见 P-28：重启前先收集）。

```markdown
# 事故：<一句话现象>          日期 / 板子身份（位流、模块、应用版本）/ 谁在操作

## 1. 现象（只写观察到的）
- 时间线（带时间戳；应用日志、内核日志、硬件状态字放在同一条时间轴上）
- 用户看到什么 / 板子表现什么

## 2. 证据（能活过重启的优先）
| 来源 | 位置 | 关键内容 |
| --- | --- | --- |

## 3. 根因分析
- 已确认：<由代码 / 日志证明的>（写依据：文件:行）
- 推断：<没有直接证据的>（标“推断”）
- 未确认：<缺证据的>（写还需要什么证据）

## 4. 修法与回退
- 改了什么（文件、函数）；回退方式
- 为什么这样修（要封住哪条触发路径）

## 5. 回归验证
- 做了什么测试、结果（次数、错误数）；板上 / 主机 / 仿真分别写

## 6. 未覆盖项（必填）
- 这次修法没有覆盖的触发路径；没有验证的部分；下一步

## 7. 固化
- 新增的规则 / 检查项 / 测试（链接到 pitfall_list 的条目）
```

# 工作流 7：一次性事件与最小必要门禁（finite event gating）

**适用场景**：让 AI 代理参与**会改变物理状态**的硬件调试（上电、下载比特流、写寄存器、DMA、重启），而操作者要为安全负责。

## 用法

给代理的提示词骨架：

```text
本次硬件动作只允许是一个“事件”（event_id = <新编号>）。流程：
1. 离线准备：候选与绑定（所有产物的 SHA-256）、无连接契约检查、停止条件、预期计数（连接 1、下载几次、run 几次……）。
2. 我提供当期现场事实（电源周期、隔离、无人佩戴、治具未变、独占保管）。你核对它们与草案一致后，才签发一次性 permit。
3. 冻结的入口只执行一次。任何偏差立即 STOP，不现场修补、不重试、不重连、不在 STOP 后查询目标。
4. 结束后事件关闭、不可重放。最终状态一律写 UNKNOWN，除非有直接证据；客户端退出不等于整板停止。
5. 失败后只允许：用保存的原始应答离线定位根因 → 最小修复 → 换新事件号。
最小必要门禁：身份、内存所有权、供电、安全状态、候选绑定。已覆盖的内容不重复仿真，但上述门禁和“实机操作有可追溯对象”的检查不得省略。
```

检查清单：

1. 事件号是否新？旧 permit / ledger / 剩余额度是否被复用？（不得复用）
2. 现场事实是操作者**当期**给出的，还是沿用旧值？（冷态不可沿用，见 P-42）
3. STOP 后有没有再碰目标？（不得）
4. 修复是否只改了根因所在的那一层？（P-36）
5. 结论措辞是否按 `claim_classification.md` 分级？

## 已验证效果

用这套流程完成了有限 DMA 事件 01–08（`report/ai_collaboration/codex_era/episodes/c01_finite_dma_events_01_08.md`）：前七次在门禁处停止，每次都用保存的原始应答定位到一个具体根因并做最小修复，
第八次得到 256 帧真实 DMA 数据（CRC32 `0xF86394C5`）。代价是文档量大、速度慢，所以配套“最小必要门禁”以避免门禁堆叠（案例 C-05）。

## 失效条件

* 事件成本很低、可以自由重试的场景（例如纯软件调试）不需要这么重。
* 操作者给出的现场事实不准确时，流程无法发现；因此要保存原始答复并允许事后更正（事件 04、08 的“现场周期填写冲突”就是这样被发现并保留的）。

# 工作流 1：新会话开场提示词（session bootstrap）

**适用场景**：长周期硬件 / 软件项目，会话会因上下文用尽或换人而中断，需要新会话在不重新粘贴历史的前提下接手。

## 用法（提示词骨架，按顺序写）

1. **一句话任务**：本会话要收口什么（例如“先按工程文件核对证据，再收口 SSVEP 信号质量与挂起问题”）。
2. **角色与边界**：新会话负责查档、分析、修改、构建、部署、测试、回退；不要把前任的操作说成自己刚完成的。
3. **项目整体介绍**：硬件、数据通路、固定映射（通道、引脚、电极位置）、启动方式、时区等**不得改动**的事实。
4. **已实现 / 未验收**：用两张清单写清楚，并给出整体状态词（例如 `IN_PROGRESS_NOT_ALL_ACCEPTED`）。
5. **证据文件清单（先读什么）**：状态索引、交接文档、关键设计文档的路径与阅读顺序；“先读顶部块，再按需回查”。
6. **硬约束 / 红线**：哪些动作需要先确认（装载 PL、重启、删除、真人）、哪些文件不能碰、临时文件放哪里、删除规程。
7. **汇报格式**：已做 / 已验证 / 没做 / 没验证 / 需要你做；数字附出处。

## 已验证效果

本项目的多个长任务会话（如案例 01 所在的会话）用这种结构接力；接手后模型第一轮汇报能指出“本轮没有登录板端、没有改产品、没有新增真人、没有删除文件”这类**未做事项**，
并在读档时发现过前任文档中的数字错误（例如某矩阵 SHA 被转述错了）。没有做对照实验，所以不声称“比其他写法更好”。

## 失效条件

* 状态索引本身过期或互相矛盾时，骨架只会把错误搬进新会话——所以第 5 条要求先读“最新块”，并在发现矛盾时写勘误块。
* 提示词过长时，模型可能漏读后半段；把硬约束放在前面，并在汇报里要求复述它理解的红线。

## 来源

2026-10-31 起的多次会话交接（案例 01 的上下文即是一个这样的新会话）。
